## 1. Executive Summary

Penny Pilot is a Next.js 15 (App Router) + Express 5/TypeScript/Prisma/PostgreSQL personal-finance application whose **financial data lives entirely in the user's own Google Drive**, not in PostgreSQL. PostgreSQL (`backend/prisma/schema.prisma`) holds only account/auth/legal/notification/activity metadata. A parallel, partially-built **Local-Only (IndexedDB) storage mode** exists on the frontend (`frontend/src/lib/storage/`) implementing a `StorageProvider` abstraction, with encrypted local backup export/import already implemented in `frontend/src/components/settings/DataStorageCard.tsx`, but the backend has **no local-storage awareness** — every protected finance route (`backend/src/app.ts`) is gated by `requireDriveConnected`, meaning Local-Only mode currently operates client-side only, independent of the backend's Drive-gated architecture. This is the most important architectural fact for the design team: **CURRENT** Drive integration is deep and mature (OAuth, workspace init, migration-account-change handling, Drive revision-based restore); **PARTIAL** Local-Only mode is real (IndexedDB CRUD, encrypted export/import, mode toggle) but not confirmed integrated into every financial page equally — **NOT VERIFIED** at full per-page depth in this pass.

Authentication and account recovery are unusually mature: a choice-based, cookie-bound `RecoverySession` state machine (email OTP / TOTP / security questions) replaced a legacy sequential flow (`backend/src/routes/auth.routes.ts`), 2FA (TOTP + backup codes), passkeys (WebAuthn, `backend/src/lib/webauthn.ts`), session-version-based hard logout, and inactivity-based session expiry are all implemented. Admins (`backend/src/routes/admin.routes.ts`) can see only account/activity/migration metadata — confirmed **no route exists** for admins to read another user's financial records; financial collections live only inside each user's Drive.

Error handling has a real, centralized Drive-error catalog (`backend/src/lib/driveErrors.ts`) mapped to actionable recovery codes (`RECONNECT_DRIVE`, `FREE_DRIVE_SPACE`, `RETRY`, `VERIFY_DATA`) consumed by `frontend/src/lib/errorActions.ts`, largely matching the Master Plan's Section 16 catalog, though the exact code list must be diffed field-by-field in a follow-up pass (**PARTIAL VERIFICATION** — driveErrors.ts confirmed, full frontend consumption of every code not exhaustively traced).

Legal/consent is implemented with versioned Terms/Privacy (`backend/src/lib/legalVersions.ts`, `backend/src/lib/legalDocuments.ts`), a `ConsentRecord` Prisma model, and PDF generation (`backend/src/services/consent/consentPdf.ts`) — consistent with Master Plan §41-44.

## 4. Backend Architecture

### 4.1 App bootstrap — `backend/src/app.ts`
- `helmet()` with production-only CSP (`default-src 'self'`, `script-src 'self'`, `style-src 'self' 'unsafe-inline'`, `img-src 'self' data: https:`, `connect-src 'self'`), HSTS in prod, `frameguard: deny`, `noSniff`, `xssFilter`.
- CORS: explicit allowlist built from `APP_URL`/`FRONTEND_URL` env vars (comma-separated, multi-domain support), `credentials: true`, methods `GET/POST/PUT/PATCH/DELETE/OPTIONS`, `exposedHeaders: ["Content-Disposition"]` (required for export/consent-PDF filenames to survive cross-origin fetch).
- **CSRF defense-in-depth**: explicit middleware rejects any `POST/PUT/PATCH/DELETE` whose `Origin` header isn't in the CORS allowlist → `403 { error: "Request origin not allowed" }`. This exists because the session cookie must be `SameSite=None` in production (cross-origin Vercel/Render deployment), which alone gives no CSRF protection.
- Baseline rate limit: `300 req / 15 min` on all of `/api`, `RATE_LIMITED` code, on top of stricter per-route limiters on auth endpoints.
- Body limit `2mb`; `cookie-parser` with `COOKIE_SECRET`.
- `GET /health` — public.
- `/api/auth` — public (contains its own per-route auth/rate-limit middleware).
- `/api/drive` — `authenticate` only (NOT `requireDriveConnected` — intentionally circular-avoidant, since Drive connection itself must be reachable pre-connection).
- `/api/transactions`, `/api/budgets`, `/api/dashboard`, `/api/investments`, `/api/bills`, `/api/goals`, `/api/savings`, `/api/analytics`, `/api/reports`, `/api/profile`, `/api/settings`, `/api/export` — ALL gated `authenticate + requireDriveConnected`. **This is the critical architectural fact: every financial data route requires an initialized Drive connection at the backend level today.** A Local-Only user bypasses this entirely by never calling these backend routes (frontend `driveStorageProvider.ts` vs `localStorageProvider.ts` decide client-side which to call — **NOT VERIFIED in full**: whether local-mode pages call these backend routes at all, or route around them completely via IndexedDB).
- `/api/notifications`, `/api/activity` — `authenticate` only, Postgres-backed, not Drive-gated (by design comment in code).
- `/api/admin` — `authenticate + requireRole("SUPER_ADMIN","ADMIN")`.
- `/api` (bare) → `referenceRoutes` (categories/accounts/payment-methods) — `authenticate` only at the app-level, with `requireDriveConnected` applied *inside* `reference.routes.ts` itself (`router.use(requireDriveConnected)`), and **must be registered last** among `/api/*` mounts per an explicit code comment, because Express matches by registration order and an earlier mount would incorrectly intercept unrelated `/api/*` paths.
- `notFoundHandler` then `errorHandler` are the final two middlewares.

### 4.2 Middleware — `backend/src/middleware/auth.ts` (NOT VERIFIED in full detail beyond names surfaced by other files)
Confirmed exports used elsewhere: `authenticate`, `requireRole`, `requireDriveConnected`, `requireRecent2FA`. Behavior inferred from usage + partial agent read:
- `authenticate`: verifies JWT from signed `access_token` cookie; 401 on missing/invalid/expired; checks `sessionVersion` for forced-logout invalidation; checks inactivity-based `sessionExpiresAt` → `401 { code: "SESSION_EXPIRED" }`.
- `requireRecent2FA`: 403 `2FA_REVERIFICATION_REQUIRED` if the user's last TOTP re-verification is older than a 12-hour window (used on `/security-questions` PATCH, `/2fa/disable`, `/change-uid`, Drive `/disconnect`, Drive `/restore/:collection`).
- `requireDriveConnected`: 403 `DRIVE_NOT_CONNECTED` for `USER` role only — admins bypass it (consistent with admins never touching financial-data routes in practice, since they have no Drive workspace of their own to gate).
- `requireRole(...)`: role allowlist check, 403 if not matched.

### 4.3 Error handling — `backend/src/middleware/errorHandler.ts`
- `ZodError` → `400 VALIDATION_INVALID_INPUT`.
- `ApiError` (custom class, thrown with `throw new ApiError(status, message, ...)` as seen in `drive.routes.ts`/`reference.routes.ts`) → its own status/code/action.
- Prisma `P2002` (unique constraint) → `409 VALIDATION_INVALID_INPUT`-style conflict.
- Prisma `P2025` (record not found) → `404`.
- CORS rejection → `403 AUTH_FORBIDDEN`.
- Fallback → `500 INTERNAL_ERROR` with a generated safe reference ID (matches Master Plan §20 "Reference: PP-ABC123" pattern — exact ID format **NOT VERIFIED** character-for-character).

### 4.4 Drive error catalog — `backend/src/lib/driveErrors.ts`
Maps raw Google API failures to typed, user-safe errors:
| Backend condition | Code | HTTP | Action hint |
|---|---|---|---|
| Storage quota exceeded | `DRIVE_STORAGE_QUOTA_EXCEEDED` | 507 | `FREE_DRIVE_SPACE` |
| Permission denied | `DRIVE_PERMISSION_DENIED` | 403 | `RECONNECT_DRIVE` |
| Auth expired/revoked | `DRIVE_AUTH_EXPIRED` | 401 | `RECONNECT_DRIVE` |
| File not found | `DRIVE_FILE_NOT_FOUND` | 404 | — |
| API unavailable (429/502/504 upstream) | `DRIVE_API_UNAVAILABLE` | 429/502/504 | `RETRY` |
| Write failed | `DRIVE_WRITE_FAILED` | 502 | `RETRY` |
| Read failed | `DRIVE_READ_FAILED` | 502 | `RETRY` |

This closely matches Master Plan §16's Google Drive catalog (`DRIVE_NOT_CONNECTED`, `DRIVE_AUTH_EXPIRED`, `DRIVE_PERMISSION_DENIED`, `DRIVE_STORAGE_QUOTA_EXCEEDED`, `DRIVE_FILE_NOT_FOUND`, `DRIVE_API_UNAVAILABLE`, `DRIVE_WRITE_FAILED`, `DRIVE_READ_FAILED`) — **CURRENT**, though `DRIVE_ACCOUNT_SWITCH_REQUIRED`/`DRIVE_MIGRATION_*` codes from the Plan were not directly confirmed inside `driveErrors.ts` in this pass (drive migration status is instead tracked via the `BackupConnection.lastConnectError` free-text field and the admin `migrationStatus.ts` service's own derived `MigrationState` enum — a **different mechanism than a dedicated error code**) — flag as **PARTIAL / DISCREPANCY vs Master Plan**: the Plan's migration-specific codes (`DRIVE_MIGRATION_STARTED/FAILED/VERIFICATION_FAILED/SUCCESS`) do not appear to exist as such; migration state is instead computed server-side from `hasLegacyData`, `connected`, `initialized`, `hasError` booleans by `deriveMigrationState()` in `backend/src/services/admin/migrationStatus.ts`.

`frontend/src/lib/errorActions.ts` → `getRecoveryAction()` consumes `err.details.action` and maps: `RECONNECT_DRIVE` → push `/connect-drive`; `FREE_DRIVE_SPACE` → open `https://drive.google.com/settings/storage`; `VERIFY_DATA` → push `/settings?tab=backup`; `RETRY` → re-invoke caller's retry callback. This is a real, working implementation of Master Plan §12/§18 ("Global Frontend Error Handler" / actionable Drive-full messaging) — **CURRENT**.

## 6. Storage Modes

### 6.1 Google Drive (CURRENT, deep implementation)
- Connect flow: `GET /api/drive/connect` → Google OAuth URL with CSRF `state` nonce (in-memory `Map`, 10-min TTL) → `GET /api/drive/callback` exchanges code, upserts `BackupConnection` (tokens encrypted), detects **account change** (different Google account than previously connected) via `accountEmail` comparison.
- **Account-change handling**: if the newly connected Google account already has an existing Penny Pilot workspace folder (`findExistingPennyPilotRoot`), the backend does **not** auto-merge — it stores a short-lived `pendingAccountChanges` choice token and redirects the frontend to `?accountChanged=1&choiceToken=...`, requiring an explicit `POST /api/drive/resolve-account-change { choiceToken, choice: "use_existing"|"start_fresh" }`. This is a faithful implementation of Master Plan §11 ("Existing Destination Workspace" — never silently merge).
- **Workspace initialization ordering**: `backupFolderId` (the "Drive is ready" signal used by `requireDriveConnected`) is set **only after** `setupWorkspace()` succeeds and verifies the write — never before. A transient failure leaves the connection "connected" (tokens saved) but not "initialized," so the app correctly keeps showing the connect/migrate screen instead of rendering against a half-set-up workspace. This is exactly the safe-flow behavior the Master Plan (§10, "Never switch source of truth before verification") demands, applied here to *initial* setup as well as migration.
- `GET /api/drive/status` → `{ configured, connected, initialized, accountEmail, hasLegacyData }`. `hasLegacyData` flags pre-Drive-migration Postgres-era accounts (see `hasLegacyPostgresData()` in `services/drive/init.ts`).
- `DELETE /api/drive/disconnect` (requires `requireRecent2FA`) — deletes the `BackupConnection` row.
- `POST /api/drive/verify` → `verifyStorage()` — an explicit, user-triggerable "verify my Drive workspace is intact" action, matching Master Plan's verification-before-trust principle.

## 12. Account Recovery UX

The actual implemented state machine (v3, choice-based) per `RecoverySession` model + `auth.routes.ts`:

```
POST /forgot-password (email)
  → recovery_token set in Secure+HttpOnly+signed cookie (never in JSON)
  → RecoverySession{state: STARTED} created (only if account exists+ACTIVE; response identical either way)
↓
POST /recovery/select-method { method: email_otp | totp | security_questions }
  → availability checked silently; unavailable method = same generic error as invalid session
  → state: METHOD_SELECTED
  → (email_otp path sends OTP immediately)
↓ (exactly one path, no chaining)
  email_otp:  POST /recovery/verify-otp {code}         — max 5 attempts, 5-min OTP TTL, resend max 3/hour w/ 60s cooldown
  totp:       POST /recovery/verify-totp {code}        — max 5 attempts, backup codes accepted
  security_qs: POST /recovery/verify-security-answers {answer1, answer2} — BOTH must match, max 5 attempts
↓
state: AUTHORIZED
↓
POST /recovery/reset-password {newPassword}
  → state: COMPLETED, consumedAt set, session single-use
  → all existing sessions invalidated (sessionVersion bump)
  → "password changed" email sent
```

Failure states confirmed in code: `LOCKED` (too many attempts on any step, or too many OTP resends) and `EXPIRED` (15-minute overall session TTL, or explicit consumption). Every failure collapses to the same `RECOVERY_GENERIC_ERROR` string (*"This recovery session is invalid or has expired. Please start over."*) — **deliberately indistinguishable** whether the cause is wrong-account, wrong-method, expired, locked, or consumed. This is a stronger security posture than the Master Plan's draft state machine (§12) which listed `EXPIRED/LOCKED/CONSUMED` as separately-named failure states — the actual implementation intentionally **merges** them into one user-facing message for security, which is a **discrepancy from the Plan's literal wording but an improvement on its intent** — flag as CURRENT + deliberate deviation, not a bug.

Legacy endpoints `POST /reset-password` and `POST /recovery-options` were **explicitly removed** (confirmed via in-code comment) because they offered a bypass around the security-question requirement — good evidence of active security hardening matching Master Plan Phase 1.

## 44. Legal / Consent UX

`ConsentRecord` model (§5), `backend/src/lib/legalVersions.ts` (exports `TERMS_VERSION`, `PRIVACY_VERSION`, confirmed imported/used by `auth.routes.ts`), `backend/src/lib/legalDocuments.ts` (likely holds the actual legal text/rendering — not read line-by-line), `backend/src/services/consent/consentPdf.ts` (generates the signed PDF). Signup requires both `termsAccepted===true` and `privacyAccepted===true` as **separate** booleans (not a single combined checkbox) — matches Master Plan §41's explicit "separate required controls" rule — CURRENT. Signature name validated by a permissive Unicode-letter regex, explicitly documented in code as allowing legitimate names in any script — good internationalization awareness. The PDF is generated best-effort at signup (inline base64 for immediate download) with a fallback re-download endpoint (`GET /api/auth/consent/download`) if the inline generation fails — a real implementation of Master Plan §43's "PDF failure must not create duplicate accounts / consent persists before claiming success" (consent DB row is created in the same transaction as the user; PDF generation happens strictly after and independently can fail without rolling back the account).
